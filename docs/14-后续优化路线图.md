# 14 · 后续优化路线图

> 原则：每一项都由**实测证据**驱动，而不是"看起来应该做"。
> 每项标注前置条件 —— 顺序错了会白做。

---

## 0. 当前基线（2026-11-24）

| 维度 | 现状 |
|---|---|
| 读吞吐 | 5,124 req/s @ 并发 10（应用直连） |
| 写吞吐 | 326 req/s @ 并发 5 → **读写的 1/16** |
| 并发饱和 | 并发 50 时吞吐反降至 1,944 req/s（单进程饱和） |
| 端到端延迟 | P50 3.2 ms（经 Nginx） |
| 高可用 | 单实例，更新/重启有 5–15 秒中断 |
| 数据层 | SQLite 单写者，多实例写入不可行 |
| 观测 | JSON 日志 + 可选 `/metrics`，无采集、无告警 |

**一句话结论**：读写不对称 + 单写者，是当前架构的两条硬边界。其余优化都在边界之内。

---

## 1. 数据层演进（最高优先级）

### 1.1 SQLite → PostgreSQL

| 项 | 内容 |
|---|---|
| 证据 | 写 326 req/s，读 5,124 req/s，差 16 倍；SQLite 单写者串行 |
| 解法 | 迁移到 PG，写操作走连接池，可横向扩展只读副本 |
| 成本 | 高（仓储层重写、迁移脚本、事务语义差异、容器编排加服务） |
| 收益 | 解锁：多实例部署、零停机发布、写入并发 |
| **前置** | 无。这是其它高可用方案的前提 |

### 1.2 不必迁移的场景

如果真实使用量是"一天十几条发布、几百次浏览"，SQLite 完全够用，**迁移反而是过度设计**。
判断标准：写入能否稳定低于 300 req/s 且不需要多实例。当前校园场景远低于此。

> 答辩要点：能说清「什么时候不该迁移」比"知道该迁移"更体现判断力。

---

## 2. 高可用与发布（依赖 1.1）

### 2.1 多实例 + 滚动更新

| 项 | 内容 |
|---|---|
| 现状 | 单容器，重建期间 5–15 秒不可用 |
| 方案 | `docker compose up --scale app=2` + Nginx upstream 轮询；`depends_on` 改为健康检查驱动 |
| 成本 | 中 |
| 收益 | 发布零中断；单实例崩溃不影响服务 |
| **前置** | 必须完成 1.1（PG），否则两实例并发写 SQLite 会锁冲突 |

### 2.2 反向代理层的健康摘除

Nginx `max_fails` / `fail_timeout` + 主动健康检查（开源版需 `nginx_upstream_check_module` 或改用 OpenResty）。
成本低，但**只有在 2.1 完成后才有意义**。

---

## 3. 观测体系完善

### 3.1 指标采集与告警

| 项 | 内容 |
|---|---|
| 现状 | `/metrics` 已实现，但没人采集；无告警 |
| 方案 | Prometheus 抓取 → Grafana 面板 → Alertmanager 规则 |
| 建议面板 | QPS、P50/P95/P99、5xx 比例、429 比例、DB up、容器内存/CPU |
| 建议告警 | 5xx > 1% 持续 5 分钟；P95 > 500ms 持续 5 分钟；`db_up == 0`；磁盘 > 85% |
| 成本 | 中（三个容器 + 配置文件） |
| 收益 | 从"出问题等人报"变成"出问题先知道" |

### 3.2 日志集中化

| 项 | 内容 |
|---|---|
| 现状 | JSON 行已具备，但散落在 `docker logs`，重启即丢（有轮转但难检索） |
| 方案 | Loki + Grafana（轻量，比 ELK 省资源）；按 `reqId` 关联两层日志 |
| 成本 | 中 |
| 收益 | 排障从"翻 grep"变成"按条件检索" |

## 4. 性能优化（边界之内，成本低）

| # | 优化 | 预期 | 成本 | 说明 |
|---|---|---|---|---|
| 4.1 | 读缓存（列表结果缓存 5–10s） | 读再提升数倍 | 低 | 注意发布/删除后失效 |
| 4.2 | 静态资源交给 Nginx 直出 | 减少 Node 处理静态请求 | 中 | 需把 `web/dist` 再打一份进 nginx 镜像 |
| 4.3 | 多进程（`cluster` / PM2） | 吃满多核 | 中 | **与 SQLite 单写者冲突**，需先解决 1.1 |
| 4.4 | 索引复核 | 数据量增长后必要 | 低 | 当前 14 条数据测不出差异，需构造大数据量再评测 |

> 注意 4.3：不解决写入模型就上多进程，只会把锁竞争放大。**顺序错了会白做**。

## 5. 安全加固

| # | 项 | 现状 | 建议 |
|---|---|---|---|
| 5.1 | 鉴权 | 无（有意简化） | 若真上线，至少加「发布者身份校验」，防止冒名发布 |
| 5.2 | CSRF | 无 | 引入 Cookie 会话后必须补；当前无 Cookie 所以风险低 |
| 5.3 | 镜像漏洞扫描 | 未做 | `trivy image sangzi-activity-hub:1.0.0` 接入 CI |
| 5.4 | SBOM | 未做 | `syft` 生成依赖清单，便于漏洞追溯 |
| 5.5 | 审计日志 | 无 | 对写操作记录「谁、何时、改了什么」，需先有身份 |
| 5.6 | 依赖锁定 | 已用 `package-lock.json` + `npm ci` | 可加 Dependabot 自动升级 PR |

> 5.1 是其它安全项的前提：**没有身份，谈授权与审计都没有意义**。

## 8. 建议的实施顺序

```
现在 ──► 5.3 镜像扫描（半天，无前置）
      ──► 3.1 指标采集 + 告警（2–3 天，无前置，收益最大）
      ──► 4.1 读缓存（1 天，无前置）
      ──► 【决策点】真实写入量是否需要 >300 req/s / 是否要多实例
              ├─ 否 → 维持 SQLite，跳到 6.1 E2E
              └─ 是 → 1.1 迁移 PG ──► 2.1 多实例 ──► 4.3 多进程
```

**决策点为什么重要**：如果真实使用量根本到不了瓶颈，为高可用付出迁移成本是负收益。
学生项目里，"判断不该做"和"做出来"同样重要。

---

## 9. 明确不做

| 项 | 理由 |
|---|---|
| Kubernetes | 单服务 + SQLite，K8s 的复杂度远超收益；真要上，先完成 1.1 与 2.1 |
| 微服务拆分 | 只有一个业务域，拆分只会增加网络调用与一致性问题 |
| 服务网格 | 同上，无多语言多服务场景 |
| 自建 CI/CD 平台 | GitHub Actions 已够用 |
