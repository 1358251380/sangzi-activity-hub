## 3. 我如何保证自己理解并能讲解

原则：生成的内容必须能自己讲清楚，并经实际执行验证。

采取的做法：

1. **设计先于代码**：先定数据模型与时间轴算法（docs/02、03），再写实现。能讲清"为什么这样设计"，而不只是"代码写了什么"。
2. **核心算法单独成纯函数**：`lib/status.js`、`lib/validate.js`、`lib/timeline.js` 都不依赖框架，可以脱开 React/Express 单独讲、单独测。
3. **每份文档都留了讲解要点**：如 [docs/03 §8](03-时间轴设计说明.md) 直接给出时间轴的口述要点。
4. **每个修复都要能复述原因**：docs/06 按"现象 → 原因 → 解决 → 收获"记录，而不是只记"改了什么"。
5. **验证不外包**：所有结论都以实际执行结果为证据（测试输出、构建体积、接口返回、截图），不采信"应该可以"。

## 5. 一个值得说明的取舍

AI 能写得比人手快，但也更容易产出"看起来对、其实有偏移"的代码。本项目的 4 个视觉缺陷（P7–P10）全部属于这一类：**接口测试 100% 通过，界面却是错的**。

因此本项目的验证分了三层，缺一层都会漏：

| 层 | 手段 | 能发现什么 |
|---|---|---|
| 逻辑层 | 164 项单元/集成测试 | 时间计算、状态派生、校验规则、接口契约 |
| 集成层 | 真实启动 + curl/Invoke-WebRequest 探测 | 生产模式托管、SPA 兜底、健康检查、404 不被吞 |
| 呈现层 | Chrome 无头截图逐页核对 | 排版、图表几何、文案取整、遮挡与溢出 |

这也是我在这个项目里最大的一条体会：**"测试通过"和"做对了"是两件事**。
