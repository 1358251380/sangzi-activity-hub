## 2. 环境配置

### 2.1 变量清单

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `3001` | 监听端口 |
| `HOST` | `0.0.0.0` | 监听地址（容器内需 0.0.0.0） |
| `NODE_ENV` | `development` | `production` 时托管 `web/dist` |
| `DB_PATH` | `./data/app.db` | SQLite 路径；相对路径按**项目根目录**解析，不依赖启动位置 |
| `CORS_ORIGIN` | `http://localhost:5173` | 仅开发期需要；生产同源不设置 |

### 2.2 配置加载策略

`server/src/index.js` 使用 `process.loadEnvFile()` 读取 `.env`，**失败即忽略**——这保证"没有 .env 也能直接跑"，降低交接时的启动失败率。

### 2.3 密钥与隐私

- `.env`、`.env.local` 在 `.gitignore` 中，不提交
- 仓库内只有 `.env.example`（无任何真实值）
- 代码中无硬编码密钥、无外部服务凭据
- 示例数据全部自编，不含真实同学姓名 / 学号 / 报名名单

## 3. 可观测性

### 3.1 健康检查

`GET /api/health` 是**业务级**健康检查，不是端口探活：

```json
{ "status": "ok", "db": "ok", "uptime": 12.4, "version": "1.0.0", "time": "..." }
```

- 数据库不可用时返回 **503** 且 `db: "error"`，编排层可据此摘流量
- Docker `HEALTHCHECK` 与 compose `healthcheck` 都指向它

> 为什么不用"端口通即健康"：SQLite 文件损坏或权限异常时端口仍然通，但服务实际已不可用。

### 3.2 请求日志

`server/src/middleware/logger.js` 输出结构化单行日志：

```
[2026-11-10T07:37:45.755Z] INFO GET /api/activities 200 3.2ms
```

- 按状态码分级：`>=500` → ERROR，`>=400` → WARN，其余 INFO
- 记录 method / 原始 URL / 状态码 / 耗时
- 测试环境通过 `logger: false` 静默，不污染测试输出

### 3.3 优雅退出

`server/src/index.js` 处理 `SIGINT` / `SIGTERM`：

1. 停止接收新连接（`server.close`）
2. 关闭数据库连接（写完 WAL）
3. 10 秒未完成则强制 `exit(1)`（定时器 `unref`，不阻塞正常退出）

同时监听 `uncaughtException` 与 `unhandledRejection`，避免异常静默丢失。

## 4. 错误处理与边界

### 4.1 统一错误结构

```json
{ "error": { "code": "...", "message": "...", "fields": { "字段": "中文提示" } } }
```

| HTTP | code | 场景 |
|---|---|---|
| 400 | `BAD_REQUEST` | 非法 ID、非法 JSON、时间轴缺 `from/to` |
| 404 | `NOT_FOUND` | 活动不存在、接口不存在 |
| 422 | `VALIDATION_FAILED` | 业务校验失败，`fields` 逐字段中文提示 |
| 500 | `INTERNAL_ERROR` | 未捕获异常（日志留堆栈，响应不含堆栈） |
| 503 | `—`（health） | 数据库不可用 |

### 4.2 边界处理清单

| 边界 | 处理方式 | 验证 |
|---|---|---|
| 结束时间早于开始时间 | 应用层 422 + 数据库 CHECK 双重拦截 | 单测 + 集成测试 |
| 报名截止晚于活动结束 | 同上 | 同上 |
| 非法日期字符串 | `normalizeDateTime` 返回 null → 逐字段报错 | 单测 |
| 超长字段 | 长度上限 + 数据库 CHECK | 单测 |
| `javascript:` 链接 | 仅允许 `http/https` 协议白名单 | 单测 |
| SQL 注入 | 全参数化语句；排序字段白名单枚举 | 单测 + 代码审查 |
| LIKE 通配符注入（`%` `_`） | 转义 + `ESCAPE '\'` | 集成测试 |
| 非法分页参数 | 夹取到合法区间（`pageSize` 0→1, 9999→100），不报错 | 单测 |
| 非数字 ID | 400 而非 500 | 集成测试 |
| 请求体非 JSON | 捕获 SyntaxError → 400 | 集成测试 |
| 删除活动时残留评论 | 外键 `ON DELETE CASCADE` | 集成测试（断言评论数归零） |
| 时间轴窗口除零 | `Math.max(W1-W0, 1)` | 单测 |
| 单日活动宽度塌缩 | CSS `min-width: 6px` 兜底 | 截图验证 |

## 5. 容器化（未本机验证）

### 5.1 设计要点

| 要点 | 做法 | 为什么 |
|---|---|---|
| 多阶段构建 | `web-build` 阶段编译前端，`runtime` 阶段只保留运行时产物 | 最终镜像不含 Vite/React 编译链，体积与攻击面更小 |
| 层缓存 | 先 `COPY package*.json` 再 `COPY .` | 改业务代码不会触发重新装依赖 |
| 非 root 运行 | `adduser -S app` + `USER app` | 容器内最小权限 |
| 数据卷 | `VOLUME ["/app/data"]` + compose `app-data` 命名卷 | **SQLite 必须落在卷上**，否则容器重建数据全丢，直接违反"数据不丢"要求 |
| healthcheck | 打 `/api/health` 而非探端口 | 能发现数据库层故障 |
| 非阻塞启动 | 启动前跑 `seed.js`（库非空自动跳过） | 首次启动即有示例数据，可重复执行 |
| 日志轮转 | compose `json-file` 限制 10m × 3 | 防止日志无限增长打满磁盘 |
| 重启策略 | `restart: unless-stopped` | 进程崩溃自动拉起 |

### 5.2 待验证清单（装上 Docker 后按此执行）

```bash
docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml ps          # 期望 healthy
curl http://localhost:3001/api/health                    # 期望 db=ok
curl -X POST http://localhost:3001/api/activities -H "Content-Type: application/json" -d '{...}'
docker compose -f deploy/docker-compose.yml restart
curl http://localhost:3001/api/activities | findstr 标题  # 期望数据仍在（验证卷挂载）
docker compose -f deploy/docker-compose.yml logs --tail=50
```

> **验收标准：步骤 5 数据仍在，才说明卷挂载正确。** 这一步是容器化里最容易漏、也最致命的检查。

## 6. 自动化与质量门禁

### 6.1 测试

```bash
npm test         # 后端测试（65 项）
npm run verify   # 后端 + 前端 + 构建产物 + 数据库 全量自检
```

| 层 | 测试 | 数量 |
|---|---|---|
| 纯函数（状态派生） | `server/test/status.test.js` | 14 |
| 纯函数（校验） | `server/test/validate.test.js` | 20 |
| HTTP 集成 | `server/test/api.test.js` | 31 |
| 纯函数（时间轴坐标） | `web/src/lib/timeline.test.js` | 14 |
| 纯函数（时间格式化） | `web/src/lib/time.test.js` | 23 |
| 接口客户端 | `web/src/api/client.test.js` | 15 |
| 本地存储 | `web/src/lib/myPublish.test.js` | 11 |
| **合计** | | **128** |

`npm run verify` 的价值：一条命令覆盖"代码对不对 + 构建产物在不在 + 数据库建没建"，适合交付前跑一遍。

> 实现细节：`scripts/verify.mjs` 逐文件调用 `node <file>` 而不是 `node --test <dir>`。Test runner 会为每个文件拉起子进程并用管道收集结果，在某些受限环境（禁止管道式 spawn）下会失败；逐文件以 `inherit` 方式运行结果等价且更稳。

### 6.2 CI

`.github/workflows/ci.yml`（GitHub Actions，Node 24）：

1. `npm --prefix server ci` → 后端测试
2. `npm --prefix web ci` → 前端纯函数测试
3. `npm --prefix web run build` → 构建门禁

⚠️ **状态：配置已就绪，尚未真实运行**（开发机未安装 git，未推送 GitHub）。推送后即可生效。

## 7. 部署脚本

| 脚本 | 用途 |
|---|---|
| `scripts/setup.ps1` | 安装前后端依赖 |
| `scripts/start.ps1` | 构建（缺失时）→ 补种子 → 生产模式启动 |
| `scripts/test.ps1` | 调用 `verify.mjs` 全量自检 |
| `scripts/start.sh` | Linux / macOS / Git Bash 等价启动 |
| `scripts/dev.mjs` | 并行启动前后端开发服务（无第三方依赖） |

> `dev.mjs` 不用 `concurrently` 的原因：少一个依赖就少一种装不上的可能，而且逻辑透明、答辩能讲清楚。

## 9. 回滚与恢复

| 场景 | 操作 |
|---|---|
| 数据损坏 | 停服务 → 备份 `data/app.db` → 删除 → 重启自动建新库 → `npm run seed` |
| 误删活动 | SQLite 无软删除。恢复方式：从 `data/app.db` 的备份还原（建议部署时定时备份该文件） |
| 版本回退 | 三方式任一：`git revert` 后重新 build / 回滚镜像 tag / 直接替换 `web/dist` 与 `server/src` |
| 数据库迁移失败 | `db.js` 的迁移在事务中执行，失败自动 `ROLLBACK`，`user_version` 不变 |

**备份建议（生产环境）**：SQLite 用文件级备份即可，但需在写入低峰执行，或使用 `sqlite3 app.db ".backup backup.db"` 做在线热备。

## 10. 已知限制

| 限制 | 说明 |
|---|---|
| 单进程 | 未做多实例部署；SQLite 单写者模型本身也不支持多写实例 |
| 无鉴权 | 任务书允许简化身份；编辑/删除权限边界是浏览器 localStorage |
| 无速率限制 | 演示项目未做；生产需在反向代理层加 |
| 无结构化 JSON 日志 | 采用单行文本日志，够用且便于 `grep`；如需接入日志系统可替换为 JSON 行格式 |
