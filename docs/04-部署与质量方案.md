### 2.2 配置加载与校验（fail-fast）

`server/src/index.js` 先用 `process.loadEnvFile()` 读取 `.env`（**失败即忽略**，保证"没有 .env 也能直接跑"），再交给 `server/src/config.js` 统一校验。

**原则：配置错误必须在启动阶段暴露，而不是运行中以奇怪的方式失败。**

| 校验项 | 规则 | 非法时的表现 |
|---|---|---|
| `PORT` | 1–65535 的整数 | 退出码 1，打印全部错误 |
| `NODE_ENV` | 仅 `development` / `production` / `test` | 同上（典型事故：写成 `prod`） |
| `DB_PATH` | 非空；相对路径按项目根解析 | 同上 |
| `LOG_FORMAT` | `json` / `text` | 同上 |
| `TRUST_PROXY` | `true`/`false`/0–10/`loopback`/`linklocal`/`uniquelocal` | 同上（不允许把拼错的字符串透传给 Express） |
| `CORS_ORIGIN` | 可空；非空须为 `http(s)://` 开头 | 同上 |

**一次报告全部错误**，不是只报第一个：

```
配置校验失败，服务拒绝启动（fail-fast）：
  - PORT 必须是 1-65535 的整数，当前值: "abc"
  - NODE_ENV 必须是 development / production / test 之一，当前值: "prod"

请对照 .env.example 修正环境变量后重试。
```

> 实测：`PORT=abc node src/index.js` → 退出码 **1**，立即退出，不会占用端口对外服务。

## 3. 可观测性

### 3.1 健康检查

`GET /api/health` 是**业务级**健康检查，不是端口探活：

```json
{ "status": "ok", "db": "ok", "uptime": 12.4, "version": "1.0.0", "time": "..." }
```

- 数据库不可用时返回 **503** 且 `db: "error"`，编排层可据此摘流量
- Docker `HEALTHCHECK` 与 compose `healthcheck` 都指向它

> 为什么不用"端口通即健康"：SQLite 文件损坏或权限异常时端口仍然通，但服务实际已不可用。

### 3.2 请求日志与请求 ID

`server/src/middleware/logger.js` 输出结构化日志，并给每个请求分配 **requestId**。

**生产（`LOG_FORMAT=json`，默认）** —— 一行一个 JSON，便于 `grep` / 日志系统采集：

```json
{"t":"2026-11-23T12:36:46.980Z","lvl":"INFO","reqId":"probe-from-edge-001","m":"GET","p":"/api/activities?pageSize=20","s":200,"ms":4.9}
{"t":"2026-11-23T12:36:46.993Z","lvl":"WARN","reqId":"50fc1af134e2","m":"GET","p":"/api/nope","s":404,"ms":0.6}
```

**开发（`LOG_FORMAT=text`，默认）** —— 便于人读：

```
[2026-11-23T12:36:46.980Z] INFO probe-from-edge-001 GET /api/activities 200 4.9ms
```

**requestId 的三处一致性**（可观测性最小闭环）：

| 位置 | 用途 |
|---|---|
| 响应头 `X-Request-Id` | 客户端 / 前端可记录，用户报错时提供 |
| 日志字段 `reqId` | 运维按号检索一次请求及其上下文 |
| 错误体 `error.requestId` | 用户看到的错误里直接带追踪号 |

- 上游反代若已注入合法 `X-Request-Id`（8–64 位 `[A-Za-z0-9._-]`），服务端**复用**它 → 跨服务日志可串联
- 级别映射：`>=500` → `ERROR`，`>=400` → `WARN`，其余 `INFO`
- 测试环境通过 `logger: false` 静默，不污染测试输出

### 3.3 静态资源缓存策略

错误的缓存策略会导致**发版后白屏**：`index.html` 被缓存住，却引用了已被替换的旧哈希资源。

| 路径 | `Cache-Control` | 理由 |
|---|---|---|
| `/assets/*`（文件名含内容哈希） | `public, max-age=31536000, immutable` | 内容变则文件名变，可永久缓存 |
| `index.html` / SPA 兜底 | `no-cache` | 每次回源校验，保证拿到最新资源引用 |
| 其它静态文件 | `max-age=3600` | 折中 |

实测：

```
GET /                                   → cache-control: no-cache
GET /assets/index-BCSZyRsr.js           → cache-control: public, max-age=31536000, immutable
```

### 3.4 JSON 响应压缩（gzip）

`server/src/middleware/compression.js`（约 50 行，零依赖）对 **JSON 响应**做 gzip：

- 触发条件：客户端 `Accept-Encoding` 含 gzip、非 HEAD、状态非 204/304、未被编码过、体积在 **1KB–1MB** 之间
- 同时设置 `Vary: Accept-Encoding`，避免共享缓存把未压缩版本发给支持压缩的客户端
- **静态资源不在此处压缩** —— 那部分交给反向代理（不占用 Node 线程），后续加 Nginx 时统一处理

实测（14 条活动列表）：

| 指标 | 值 |
|---|---|
| 未压缩 | 7,864 字节 |
| gzip 后 | 2,310 字节 |
| 压缩率 | **-70.6%** |

### 3.5 优雅退出

`server/src/index.js` 处理 `SIGINT` / `SIGTERM`：

1. 停止接收新连接（`server.close`）
2. 关闭数据库连接（写完 WAL）
3. 10 秒未完成则强制 `exit(1)`（定时器 `unref`，不阻塞正常退出）

同时监听 `uncaughtException` 与 `unhandledRejection`，避免异常静默丢失。

## 4. 错误处理与边界

### 4.1 统一错误结构

```json
{ "error": { "code": "...", "message": "...", "fields": { "字段": "中文提示" }, "requestId": "50fc1af134e2" } }
```

`requestId` 与响应头 `X-Request-Id`、日志字段 `reqId` 三处一致，用于把用户报错与后台日志对应起来。

| HTTP | code | 场景 |
|---|---|---|
| 400 | `BAD_REQUEST` | 非法 ID、非法 JSON、时间轴缺 `from/to` |
| 404 | `NOT_FOUND` | 活动不存在、接口不存在 |
| 422 | `VALIDATION_FAILED` | 业务校验失败，`fields` 逐字段中文提示 |
| 500 | `INTERNAL_ERROR` | 未捕获异常（日志留堆栈，响应不含堆栈） |
| 503 | `—`（health） | 数据库不可用 |

### 4.2 边界处理清单

| 边界 | 处理方式 | 验证 |
|---|---|---|
| 结束时间早于开始时间 | 应用层 422 + 数据库 CHECK 双重拦截 | 单测 + 集成测试 |
| 报名截止晚于活动结束 | 同上 | 同上 |
| 非法日期字符串 | `normalizeDateTime` 返回 null → 逐字段报错 | 单测 |
| 超长字段 | 长度上限 + 数据库 CHECK | 单测 |
| `javascript:` 链接 | 仅允许 `http/https` 协议白名单 | 单测 |
| SQL 注入 | 全参数化语句；排序字段白名单枚举 | 单测 + 代码审查 |
| LIKE 通配符注入（`%` `_`） | 转义 + `ESCAPE '\'` | 集成测试 |
| 非法分页参数 | 夹取到合法区间（`pageSize` 0→1, 9999→100），不报错 | 单测 |
| 非数字 ID | 400 而非 500 | 集成测试 |
| 请求体非 JSON | 捕获 SyntaxError → 400 | 集成测试 |
| 删除活动时残留评论 | 外键 `ON DELETE CASCADE` | 集成测试（断言评论数归零） |
| 时间轴窗口除零 | `Math.max(W1-W0, 1)` | 单测 |
| 单日活动宽度塌缩 | CSS `min-width: 6px` 兜底 | 截图验证 |

## 5. 容器化（未本机验证）

### 5.1 设计要点

| 要点 | 做法 | 为什么 |
|---|---|---|
| 多阶段构建 | `web-build` 阶段编译前端，`runtime` 阶段只保留运行时产物 | 最终镜像不含 Vite/React 编译链，体积与攻击面更小 |
| 层缓存 | 先 `COPY package*.json` 再 `COPY .` | 改业务代码不会触发重新装依赖 |
| 非 root 运行 | `adduser -S app` + `USER app` | 容器内最小权限 |
| 数据卷 | `VOLUME ["/app/data"]` + compose `app-data` 命名卷 | **SQLite 必须落在卷上**，否则容器重建数据全丢，直接违反"数据不丢"要求 |
| healthcheck | 打 `/api/health` 而非探端口 | 能发现数据库层故障 |
| 非阻塞启动 | 启动前跑 `seed.js`（库非空自动跳过） | 首次启动即有示例数据，可重复执行 |
| 日志轮转 | compose `json-file` 限制 10m × 3 | 防止日志无限增长打满磁盘 |
| 重启策略 | `restart: unless-stopped` | 进程崩溃自动拉起 |

### 5.3 Nginx 反向代理与 TLS（2026-11-23 新增）

**拓扑**：应用容器不再对外发布端口，所有流量必须经过网关。

```
浏览器 ──► nginx :8080 / :8443 ──► app:3001（compose 内网，宿主不可直连）
              │                        │
       TLS / gzip / 限流 / 安全头    业务 API + 前端产物
```

**为什么要把后端藏到内网**：流量入口唯一，才能保证 TLS、限流、安全头、审计**不可绕过**。如果应用仍对外暴露 3001，任何人都能绕过限流直连后端。

**Nginx 承担的职责**

| 能力 | 配置点 | 实测 |
|---|---|---|
| TLS 终止（TLSv1.2/1.3 + HTTP/2） | `listen 443 ssl; http2 on;` | ✅ `https://localhost:8443` 返回 200，`Strict-Transport-Security: max-age=31536000` |
| gzip（含静态资源） | `gzip on; gzip_types ...` | ✅ API 响应 8,325 → 2,395 字节（-71%） |
| 限流 | `limit_req_zone ... rate=20r/s; burst=40 nodelay` | ✅ 80 并发 → **42×200 + 38×429**，429 在网关层返回、未打到应用 |
| 安全响应头 | `X-Content-Type-Options` / `X-Frame-Options: DENY` / `Referrer-Policy` / `Permissions-Policy` | ✅ 全部存在 |
| 请求体上限 | `client_max_body_size 1m`（应用层 100kb 双保险） | ✅ |
| 网关自身健康检查 | `location = /healthz` 直接返回 `ok`，不碰后端 | ✅ 200 `ok` |
| 请求标识注入 | `proxy_set_header X-Request-Id $request_id;` | ✅ 见下 |
| 隐藏版本号 | `server_tokens off;` | ✅ `Server: nginx`（无版本） |

**跨层追踪（关键设计）**

Nginx 为每个请求生成 `$request_id`（32 位十六进制），通过 `X-Request-Id` 传给应用；应用识别为合法 ID 后**复用**而不是另生成一个。于是同一个 ID 同时出现在 nginx access log 与 app 日志里：

```
nginx: {"reqId":"d64109e68d1b3b102c105e9289fc9a77","m":"GET","p":"/api/activities","s":200,"rt":0.004,"upstream":"172.18.0.3:3001"}
app  : {"reqId":"d64109e68d1b3b102c105e9289fc9a77","m":"GET","p":"/api/activities","s":200,"ms":4.3}
```

**实测**：45 个经反代的请求，**45 个 ID 在两层日志中完全匹配**；另有 38 个被限流拒绝的请求只有 nginx 记录、应用无记录 —— 证明限流确实发生在网关层。

**证书管理**

- 自签证书由 `npm run cert`（`scripts/gen-cert.ps1` / `gen-cert.sh`）生成，SAN 含 `DNS:localhost, IP:127.0.0.1`
- **`deploy/nginx/certs/` 已加入 `.gitignore`** —— 私钥绝不入库
- 证书目录以只读方式挂载进容器（`:ro`）
- 首次启动前必须先生成证书，否则 nginx 会因 `cannot load certificate` 启动失败（这是设计上的 fail-fast，不是 bug）

**端到端性能影响**（详见 [docs/12](12-容量基线与压测.md)）

| 路径 | P50 |
|---|---|
| 应用直连 | 1.7 ms |
| 经 Nginx | 3.2 ms |

多 1.5 ms 换 TLS + 限流 + 安全头 + 统一入口，性价比合理。

## 9. 备份与恢复

### 9.1 备份（`npm run backup`）

`scripts/backup.mjs` 用 SQLite 的 **`VACUUM INTO`** 做**在线热备**。

**为什么不能直接复制 `app.db`**：项目开了 WAL 模式，最新写入可能还在 `-wal` 文件里，裸拷可能得到缺最后若干次提交、甚至不一致的快照。`VACUUM INTO` 在一个读事务里生成一致快照，且不需要停服务。

脚本行为：

| 步骤 | 说明 |
|---|---|
| 1. 生成快照 | `VACUUM INTO 'data/backups/app-YYYYMMDD-HHMMSS.db'` |
| 2. 校验备份 | 打开备份 → `PRAGMA integrity_check` 必须为 `ok` → 统计 activities / comments 行数 |
| 3. 保留策略 | 默认保留最近 **7** 份（`BACKUP_KEEP` 可调），按固定宽度文件名排序即时间序 |
| 4. 退出码 | 成功 0、失败 1（便于接 CI / 计划任务） |

实测输出：

```json
{
  "ok": true,
  "dbPath": "D:\\作品\\工作台\\桑梓项目\\data\\app.db",
  "backup": "D:\\作品\\工作台\\桑梓项目\\data\\backups\\app-20261123-123632.db",
  "sizeBytes": 53248,
  "integrity": "ok",
  "activities": 14,
  "comments": 4,
  "keep": 7
}
```

> 生产环境可挂计划任务/定时器定期执行，例如每小时一次。

### 9.2 恢复演练（`npm run backup:drill`）

**「有备份」和「备份能恢复」是两件事。** 没演练过的备份等于没有备份。

`scripts/backup-restore-drill.mjs` 在**系统临时目录**里完整演练一遍，**不碰真实数据**：

| # | 步骤 |
|---|---|
| 1 | 临时目录建库 + 写入 14 条示例数据 |
| 2 | `VACUUM INTO` 热备 |
| 3 | 备份文件自检（完整性 + 行数与原始一致） |
| 4 | **模拟灾难**：删除 `app.db` 及 `-wal` / `-shm` |
| 5 | 从备份还原 |
| 6 | 恢复后校验（能打开 + 完整性 + 行数一致） |
| 7 | 用应用自身的 `openDatabase` 打开，确认迁移路径正常 |

实测：**7/7 步通过**，`{"ok":true,"totalSteps":7,"failed":[]}`。

### 9.3 真实恢复流程（故障时照做）

| 场景 | 操作 |
|---|---|
| 数据损坏 | 停服务 → `npm run backup`（若库还能读）→ 用备份还原 → 重启 |
| 误删活动 | SQLite 无软删除，只能从最近备份还原（**这也是为什么要定期备份**） |
| 从备份还原 | 停服务 → 备份当前库 → 把 `data/backups/app-<时间>.db` 复制为 `data/app.db` → 删掉遗留的 `-wal`/`-shm` → 重启 |
| 版本回退 | `git revert` 后重新 build / 回滚镜像 tag / 直接替换 `web/dist` 与 `server/src` |
| 数据库迁移失败 | `db.js` 的迁移在事务中执行，失败自动 `ROLLBACK`，`user_version` 不变 |

## 10. 已知限制

| 限制 | 说明 |
|---|---|
| 单进程 | 未做多实例部署；SQLite 单写者模型本身也不支持多写实例 |
| 无鉴权 | 有意简化身份；编辑 / 删除权限边界是浏览器 localStorage |
| 无速率限制 | 演示项目未做；生产需在反向代理层加 |
| 无结构化 JSON 日志 | 采用单行文本日志，够用且便于 `grep`；如需接入日志系统可替换为 JSON 行格式 |
