# 01 · 需求与功能清单

> 对应任务书「二、基础要求（必做）」与「三、选做进阶」。
> 每条功能均带**验收标准**，用于第 4 阶段测试记录对照。

---

## 1. 用户与场景

| 角色 | 谁会用到 | 典型场景 | 关键诉求 |
|---|---|---|---|
| **浏览者（同学）** | 全校学生 | "下周二有什么讲座？""这个比赛几号截止报名？" | 一眼看到**时间**，能搜到、能筛到 |
| **发布者·学院** | 学院教务/学生会 | 发布学科竞赛、讲座 | 信息权威、覆盖面广 |
| **发布者·学生组织** | 社团、学生会部门 | 发布活动安排、招新 | 长期可见、能持续更新 |
| **发布者·个人** | 任何同学 | 转发自己知道的机会 | 门槛低、一次录入 |
| **评论者** | 浏览者兼任 | "报名要交什么材料？""去年这题考了啥？" | 补充报名经验，靠近关键信息 |

**核心用户旅程**：

```
发现活动 → 看时间是否冲突 → 看报名截止还有多久 → 看详情/参与方式
        → 看别人评论（材料/难度/经验） → 决定报名
```

三个断点即本项目的三个设计焦点：**聚合（一处看全）→ 时间（是否来得及/是否冲突）→ 交流（值不值得去）**。

## 2. P0 必须完成（基础要求，缺一即不合格）

### F1 活动浏览列表

| 项 | 内容 |
|---|---|
| 任务书条目 | 二.1 活动浏览与详情 |
| 要求 | 卡片/列表展示，含：活动名称、类型、发布者、开始时间、结束时间、报名截止时间；能区分发布者是学院/学生组织/个人 |
| 验收标准 | ① 首页卡片同时可见上述 5 个时间与归属字段 ② 发布者类型有**视觉上可区分**的标签（颜色+文案），不依赖文字细读 ③ 报名截止与活动起止**视觉上分离**，不被误读为同一时间 |

### F2 活动详情

| 项 | 内容 |
|---|---|
| 任务书条目 | 二.1 |
| 要求 | 详情含：活动介绍、参与方式或相关链接；示例数据需注明 |
| 验收标准 | ① 详情页展示完整介绍与链接（链接可点击、新窗口打开） ② 页面标注"示例数据"说明 ③ 展示报名截止倒计时/相对时间 |

### F3 时间轴（★ 核心）

| 项 | 内容 |
|---|---|
| 任务书条目 | 二.2 |
| 要求 | 按时间展示活动，**体现持续跨度**；**报名截止与举办活动是两个不同时间**，需区分；形式不限 |
| 验收标准 | ① 多日活动色条长度与天数成正比，**跨天可见跨度**，非普通列表 ② 报名截止以**独立标记**（区别于色条）呈现 ③ 任务书原文样例必须通过：10/20 截止报名、11/15–16 举行的竞赛，时间轴上同时可读 ④ 可切换时间窗口（周/月/季），有"今天"基准线、有图例 |

### F4 活动发布

| 项 | 内容 |
|---|---|
| 任务书条目 | 二.3 |
| 要求 | 表单含：名称、类型、发布者类型、发布者名称、面向对象（含"全校"）、开始时间、结束时间、报名截止时间、活动介绍 |
| 验收标准 | ① 9 个字段齐全 ② 校验规则全部生效（见下表） ③ 身份**下拉选择**即可，不做真实账号 ④ 提交成功有明确反馈并跳转/回填 |

**校验规则（服务端为准，前端同步提示）**

| 规则 | 提示文案 |
|---|---|
| 必填项为空 | "「活动名称」不能为空" |
| 结束时间早于开始时间 | "结束时间不能早于开始时间" |
| 报名截止晚于活动结束 | "报名截止时间不能晚于活动结束时间" |
| 名称超长（>100 字） | "活动名称不能超过 100 字" |
| 介绍超长（>5000 字） | "活动介绍不能超过 5000 字" |
| 评论内容为空 | "评论内容不能为空" |
| 评论超长（>500 字） | "评论内容不能超过 500 字" |

### F5 搜索与筛选

| 项 | 内容 |
|---|---|
| 任务书条目 | 二.4 |
| 要求 | 至少一种查找方式；建议关键词搜索 + 类型筛选，有余力加学院筛选 |
| 验收标准 | ① 关键词搜标题与介绍 ② 活动类型筛选 ③ 发布者类型筛选 ④ 面向对象筛选 ⑤ 条件可组合、可一键清空、结果为空有友好提示 |

### F6 评论与注意事项

| 项 | 内容 |
|---|---|
| 任务书条目 | 二.5 |
| 要求 | 详情下可查看/发表评论；至少含昵称、内容、发表时间；内容非空 |
| 验收标准 | ① 评论列表按时间倒序，显示昵称/内容/时间 ② 发表后立即出现，无需刷新 ③ 空内容被拒并提示 ④ 评论数在列表页可见 |

### F7 数据保存与可用性

| 项 | 内容 |
|---|---|
| 任务书条目 | 二.6 |
| 要求 | 操作后有明确提示；刷新后数据不丢；导航清晰；PC 可用；移动适配算加分 |
| 验收标准 | ① **刷新页面后新增活动与评论仍在**（SQLite 持久化） ② 所有写操作有成功/失败 toast ③ 顶部导航常驻，可直达 4 个主页面 ④ 1280px 宽度下无横向滚动 ⑤ 375px 宽度下可正常浏览（加分） |

## 3. P1 选做（按运维方向，建议做 3–4 项，按投入产出排序）

任务书原文："基础部分做完后再考虑这一部分，不用全做。建议挑 1–3 项做好，**做得多不如做得稳**。"
任务书对运维/研发方向的指引："优先从「数据与工程」和「部署与质量」里选。"

| # | 选做项 | 所属方向 | 成本 | 得分权重 | 决策 |
|---|---|---|---|---|---|
| S1 | **用数据库保存数据** | 数据与工程 | 低（已内建） | ★★★★★ | ✅ 必做 |
| S2 | **前后端分离，后端提供接口** | 数据与工程 | 中（已内建） | ★★★★★ | ✅ 必做 |
| S3 | **数据模型 + 表结构说明** | 数据与工程 | 低 | ★★★★ | ✅ 必做 |
| S4 | **活动状态（报名中/进行中/已结束）** | 内容管理 | 低（派生字段） | ★★★★ | ✅ 做 |
| S5 | **编写测试用例** | 部署与质量 | 中 | ★★★★ | ✅ 做 |
| S6 | **Docker 一键启动** | 部署与质量 | 中 | ★★★★ | ✅ 做（依赖 R2） |
| S7 | **部署脚本** | 部署与质量 | 低 | ★★★ | ✅ 做 |
| S8 | **完善错误提示与边界处理** | 部署与质量 | 中 | ★★★ | ✅ 做 |
| S9 | **编辑/删除自己发布的活动** | 内容管理 | 中 | ★★★ | 做（业务闭环） |
| S10 | **截止提醒（模拟）** | 活动互动 | 低 | ★★★ | 备选 |
| S11 | 可访问演示地址 | 部署与质量 | 高（需公网/内网穿透） | ★★ | ⚠️ 视条件 |
| S12 | CI（GitHub Actions） | 部署与质量 | 中（需 git） | ★★★ | 备选（依赖 R1） |
| S13 | 时间线与月历切换 | 浏览体验 | 高 | ★★ | 备选 |
| S14 | 收藏 / 关注 | 浏览体验 | 中 | ★★ | 不做 |
| S15 | 管理员审核 | 内容管理 | 高 | ★★ | 不做 |
| S16 | Logo 设计 | 品牌设计 | 中 | ★ | 不做（非运维方向主项） |

**结论：主攻「数据与工程」+「部署与质量」两个方向，共 9 项（S1–S9）。**
理由：这 9 项中 7 项是任务书点名的加分方向，且与运维身份强相关；S4/S5/S8 成本低、展示度高。放弃 S14–S16，避免"样样半成品"。

## 4. P2 明确不做

| 项 | 理由 |
|---|---|
| 真实账号/登录/鉴权 | 任务书明确允许简化："发布时直接选择身份就行" |
| 对接学校接口、统一身份认证 | 任务书明确不需要 |
| 真实通知推送 | 任务书标注"模拟即可" |
| 报名名单收集 | 任务书边界：**不得收集真实同学个人信息和报名名单** |
| 服务器采购 / 正式上线 | 任务书不要求 |

## 5. 非功能需求

| 维度 | 要求 | 验证方式 |
|---|---|---|
| 性能 | 首页 200 条活动渲染 < 1s；API P95 < 200ms（本地） | 手工计时 + 请求日志 |
| 数据量 | 种子数据 ≥ 12 条，覆盖全部边界场景 | 见 03 文档样例表 |
| 时区 | 统一以 `Asia/Shanghai` 展示，存储用 UTC ISO | 单测 |
| 可用性 | 后端异常返回结构化错误，前端不白屏 | 错误注入测试 |
| 可维护性 | 核心纯函数（校验/状态/时间轴坐标）有单测 | `pnpm test` |
| 可运行性 | 新机器按 README 三步内启动成功 | 第 4 阶段模拟验证 |
