# 03 · 时间轴设计说明

> 本项目的**核心技术点**，也是最容易被做浅的一环——一旦退化成普通列表，这个系统就失去了存在意义。
> 实现文件：`web/src/lib/timeline.js`（纯函数，单测覆盖）+ `components/TimelineChart.jsx`（渲染）

---

## 1. 设计约束

1. "按时间展示活动，**能看出每个活动从哪天持续到哪天**。**持续多天的活动要体现出时间跨度，只做一个普通列表不算完成**。"
2. "**报名截止和活动举办是两个不同的时间，需要区分开**。比如一场竞赛 10 月 20 日截止报名，11 月 15 至 16 日举行，时间轴上要能看清这两件事。"
3. 形式不限：横向时间条、纵向时间线、月历均可。

**翻译成技术约束**：一个活动必须在同一视图上同时表达

- **一个区间**（活动举办：`startAt` → `endAt`，长度可变）
- **一个时刻**（报名截止：`signupDeadline`，单点）

---

## 2. 视图选型决策

| 视图 | 跨度表达 | 单点标记 | 跨月处理 | 实现成本 | 结论 |
|---|---|---|---|---|---|
| **横向甘特条** | ★★★★★ 长度∝天数 | ★★★★★ 易叠加 | **自动正确**（连续坐标） | 中 | ✅ **主视图** |
| 纵向时间线 | ★★ 弱（易退化成列表） | ★★★ | 自动 | 低 | ❌ 主视图不用（有被判"普通列表"的风险） |
| 月历 | ★★★★ 需按天切段 | ★★★★ | **需特殊处理**：跨格活动要拆成多段渲染 | 高 | ⚠️ 未实现 |

**决策**：主视图用**横向甘特条 + 连续时间坐标**。

理由：连续坐标下"跨月/跨年"天然正确——因为坐标是时间的线性映射，不关心月份边界。而月历视图因为按"格"离散化，跨格活动必须切成多段再画，是本题最容易翻车的地方。**用甘特条先锁死核心要求，月历留作后续扩展。**

## 3. 坐标系统

### 3.1 三段式分层

```
① 数据层   activities: [{startAt, endAt, signupDeadline, ...}]        (ISO 字符串)
        ↓  windowOf(anchorDate, span)  生成可视窗口 [wStart, wEnd]（毫秒）
② 投影层   buildTimeline(activities, window) → { rows, ticks, todayRatio }
        ↓  纯函数，输入输出全是数据，不碰 DOM
③ 渲染层   <TimelineChart> 用百分比定位 + CSS 变量上色
```

**关键**：② 是纯函数，所有边界情况都能在没有浏览器的情况下单测。这是把"最容易出错的部分"隔离出来的设计。

### 3.2 映射公式

设窗口为 `[W0, W1]`（毫秒），总宽 `span = W1 - W0`：

```
ratio(t)   = (t - W0) / span                  // 归一化到 0..1
left%      = ratio(clamp(barStart)) * 100
width%     = (ratio(clamp(barEnd)) - ratio(clamp(barStart))) * 100

barStart   = max(startAt, W0)                 // 裁剪到窗口内
barEnd     = min(endAt,   W1)
```

活动可见性：`barStart <= barEnd`（即 `startAt <= W1 && endAt >= W0`，与后端 `/api/timeline` 的筛选条件一致）。

### 3.3 色条与标记

| 元素 | 表达 | 实现 |
|---|---|---|
| 活动区间 | 圆角色条，宽度 ∝ 持续时长 | `left/width` 百分比定位，`min-width: 6px` 保证单日活动可见 |
| **报名截止** | 色条上叠加**菱形 + 虚线标记**，下方「报名截止」文案 | 独立的 `deadlinePct` 定位，`z-index` 高于色条 |
| 今天 | 贯穿全高的红色竖向基准线 + 轴内「今天」标签 | `todayPct` |
| 时间刻度 | 顶部轴：按窗口长度自适应粒度 | 见 §3.5 |
| 状态 | 色条底色按 `status` 固定配色：报名中 `#059669` / 报名已截止 `#64748b` / 进行中 `#2563eb`（另加描边高亮）/ 已结束 `#cbd5e1`（另降透明） | `STATUS_BAR_COLORS` + CSS 类名 |

> 为什么要 `min-width: 6px`：单日活动在 3 个月窗口下宽度可能不足 1px，会"消失"，造成"活动缺失"的错误观感。

#### 3.3.1 标题的摆放策略（实测修正）

最初把标题一律放在色条内部。实测发现月视图下 2 天以内的活动仅占约 6.7% 宽度（≈60px），9 个汉字装不下，会被 `overflow: hidden` 裁成"第七届""月"这类碎片。

改为**按可用宽度分两路**：

| 色条宽度 | 标题位置 |
|---|---|
| ≥ 18% | 色条内部（白字、省略溢出） |
| < 18% | 色条**外侧**右侧；右侧剩余不足 24% 时改放左侧 |

之所以可以放外侧：**每行只渲染一个活动**（见 §3.4），行内不会互相遮挡。

配套细节：外侧标题偏移 16px（覆盖 `min-width: 6px` 撑开的色块，避免遮住首字），并加半透明白底，使其压在网格线上仍然可读。

> 这条修正的排查过程记录在 [docs/06 §P8、§P9](06-问题排查记录.md)。

### 3.4 行布局

**一条活动一行**，不做区间打包（interval packing）。

理由：
- 要让读者看出每个活动从哪天持续到哪天，**逐行对齐日期轴**是信息密度最高的方式，可横向比较；
- 打包会引入行号分配，读者难以追踪同一条活动；
- 数量级只有几十条，行高足够。

可选优化：按 `startAt` 升序排列，同起始时间按持续时长降序。

### 3.5 刻度自适应

| 窗口跨度 | 刻度粒度 | 标签格式 |
|---|---|---|
| ≤ 14 天 | 每天 | `11-15` |
| ≤ 70 天（约 2 个月） | 每周（周一） | `11-16` |
| ≤ 730 天 | 每月 1 日 | `11月` |
| > 730 天 | 每年 1 月 1 日 | `2026` |

刻度位置同样用 `ratio(t)*100` 计算，与色条共用同一坐标系，保证对齐。

### 3.6 窗口切换

| 模式 | 窗口 | 默认锚点 |
|---|---|---|
| 周 | 今天所在周的周一 → 周日 | 今天 |
| 月 | 当月 1 日 → 次月 1 日 | 今天 |
| 季 | 当季首月 1 日 → 3 个月后 | 今天 |

支持「上一页 / 今天 / 下一页」平移。所有计算走 `dayjs`，避免手写日期运算。

## 4. 算法伪代码

```js
// web/src/lib/timeline.js

export function buildTimeline(activities, window, now = new Date()) {
  const W0 = window.start.getTime()
  const W1 = window.end.getTime()
  const span = Math.max(W1 - W0, 1)          // 防除零
  const clampPct = (t) =>
    Math.min(100, Math.max(0, ((t - W0) / span) * 100))

  const rows = activities
    .map((a) => {
      const s = Date.parse(a.startAt)
      const e = Date.parse(a.endAt)
      const d = Date.parse(a.signupDeadline)
      if (s > W1 || e < W0) return null        // 与窗口无交集

      const barStart = Math.max(s, W0)
      const barEnd = Math.min(e, W1)
      const leftPct = clampPct(barStart)
      const rightPct = clampPct(barEnd)
      const widthPct = Math.max(rightPct - leftPct, 0)

      const deadlineInWindow = d >= W0 && d <= W1
      const deadlinePct = clampPct(d)

      return {
        activity: a,
        leftPct,
        widthPct,
        clippedStart: s < W0,                  // 左端被裁 → 渲染成平头 + 箭头
        clippedEnd: e > W1,                    // 右端被裁
        deadlinePct,
        deadlineInWindow,
        deadlinePctBefore: d < W0,             // 截止已过 → 左侧边界显示「已截止」
        isSingleDay: e - s < 86400000,
        durationDays: Math.ceil((e - s) / 86400000),
      }
    })
    .filter(Boolean)
    .sort((x, y) => Date.parse(x.activity.startAt) - Date.parse(y.activity.startAt))

  return {
    rows,
    ticks: buildTicks(W0, W1),
    todayPct: now.getTime() >= W0 && now.getTime() <= W1
      ? clampPct(now.getTime())
      : null,
    empty: rows.length === 0,
  }
}
```

| # | 场景 | 数据设计 | 期望表现 |
|---|---|---|---|

| E3 | 跨 2 日 | 10-20 → 10-21 | 宽度约为单日的 2 倍 |
| E4 | 跨月 | 10-28 → 11-03 | 连续色条**不被月份边界打断**（甘特条相对月历的优势） |
| E5 | 跨年 | 12-30 → 次年 01-02 | 同上，标签正确显示年份 |
| E6 | 长期活动 | 持续 30 天 | 在月视图中横跨几乎整屏，端点被裁剪并显示箭头 |
| E7 | 报名截止早于窗口（已过） | 截止 09-30，活动 11-15 | 左侧边界显示「报名已截止」提示，而非错误定位 |
| E8 | 进行中但仍可报名 | 开始 11-01，截止 11-20，结束 11-30 | 状态=进行中，且显示"仍可报名"（正交状态验证） |

| E13 | 极窄窗口 | 周视图 + 30 天长活动 | 色条铺满整行两端夹箭头 |
| E14 | 同为一天的截止与开始 | 截止 10-20 23:59，活动 10-20 09:00（同日） | 标记与色条起点在同一天，位置不重叠错乱 |

## 6. 单测要点（`web/src/lib/timeline.test.js`）

| 测试 | 断言 |
|---|---|
| 坐标线性性 | 窗口中点的活动，`leftPct ≈ 50` |
| 裁剪正确 | 活动早于窗口时 `leftPct === 0` 且 `clippedStart === true` |
| 无交集过滤 | 窗口外活动产生 0 行 |
| 除零保护 | `window.start === window.end` 不抛异常 |
| 跨月不断条 | 跨月活动 `widthPct` 等于两端 ratio 差，不受月份影响 |
| 截止点定位 | `deadlinePct` 与手工计算一致（±0.01） |
| 今日线 | `todayPct` 在窗口内时非 null，窗口外为 null |
| 排序 | 结果按 `startAt` 升序 |
| 单日最小宽度 | `isSingleDay === true` 时由 CSS 兜底（样式层断言） |

若后续追加月历视图，**不要复用甘特条的行数据**：月历需按"天格"离散化，跨格活动要切成多段：

```js
// 将一个活动按自然日切段，每段渲染进对应日期格
splitByDay(activity) → [{ day: '2026-10-28', isFirst, isLast }, ...]
```

首段切左圆角、末段切右圆角、中间段直边 —— 这是月历"跨多格"表达的关键。
当前**不在主计划内**，仅在有富余时间时追加，且不影响主视图。

## 8. 实现要点（便于对外讲解）

1. **为什么不用普通列表 / 纵向时间线**：普通列表无法表达"跨度"；纵向时间线也难以让人横向比较区间长度。
2. **怎么同时表达两个时间**：活动是一个**区间**→宽度；报名截止是一个**时刻**→标记点。两者用同一套 `ratio(t)` 坐标映射，所以永远对齐。
3. **跨月/跨年为什么不难**：坐标是连续时间的线性映射，不按月切格；难的是月历视图（要按天切段），所以主视图选甘特条。
4. **最容易出错的地方**：窗口裁剪（`max/min` 到窗口边界）和单日活动宽度塌缩（`min-width` 兜底）。这两条都有单测。
5. **为什么坐标计算放纯函数**：把边界情况从 UI 里隔离出来，能离线单测，改样式不影响正确性。
