# 06 · 问题排查记录

> 任务书答辩要求「讲清楚遇到的问题和解决办法」。本文按 **现象 → 定位 → 原因 → 解决 → 收获** 记录真实排查过程，不含虚构。

## 第 1 组 · 环境与工具链

这些问题有一个共同根因：**运行在受限沙箱中，禁止跨进程管道通信（named pipe / piped stdio）**。这组记录的价值在于说明"同一类错误如何归因"，而不是逐个碰运气。

### P1 工作区无法写入，连命令都起不来

**现象**
```
Error: SetNamedSecurityInfoW failed (Win32 5): grantWrite(D:\作品\工作台\桑梓项目)
```
任何 shell 命令都无法执行。

**定位**
Win32 错误码 5 = `ERROR_ACCESS_DENIED`。检查工作区目录的实际权限：当前用户虽是 owner，但缺少 `WRITE_OWNER` 有效权限，导致运行时无法为沙箱授予工作区写权限。

**解决**
用权限诊断脚本一次性完成"备份 DACL → 补齐当前用户 FullControl → 重新读取验证"。

关键点：**先备份再改，并且保留回滚命令**。改完后重新读取 ACL 确认 `writeOwner: false → true`，再重试原操作。

**收获**
权限类问题要先区分"无权限"和"ACL 结构缺陷"——前者加权限即可，后者必须改 DACL 本身。任何 DACL 修改都要先留备份。

### P2 npm install 失败：缓存目录在工作区外

**现象**
```
npm error The operation was rejected by your operating system.
npm error requiredBy: '.'
```

**定位**
读 npm 的 debug log，失败点在写 `C:\Users\<user>\AppData\Local\npm-cache\_logs`——缓存目录在工作区之外，被沙箱拒绝；此时连日志都写不出来，所以报错信息很含糊。

**解决**
把缓存重定向到工作区内：

```bash
npm --prefix server install --cache ./.npm-cache
```

**收获**
`npm` 的错误信息经常只暴露最后一步失败，真正的原因要看 `_logs/*-debug-0.log`。凡是"权限类"报错，先确认工具写入的**所有路径**是否都在允许范围内——包括缓存、临时目录、日志目录。

### P3 `node --test test/` 全部失败：spawn EPERM

**现象**
```
Error: spawn EPERM
  at ChildProcess.spawn (node:internal/child_process)
```

**定位**
Node 的 test runner 会为**每个测试文件**拉起子进程，并通过**管道**收集结果。受限环境禁止管道式 stdio，于是 spawn 直接失败——注意：**测试代码本身一行都没跑**，这不是测试逻辑的错误。

**解决**
有两种路径：

1. 逐文件直接运行（进程内执行，结果等价）：`node test/status.test.js`
2. 在 `scripts/verify.mjs` 里用 `stdio: 'inherit'` 而不是管道

项目采用路径 2，并保留了标准的 `npm test` 给正常环境使用。

**收获**
看到 `spawn EPERM` 先问"是谁在 spawn 谁、用的什么 stdio"。`inherit` 不需要管道，通常不受限；`pipe` 才需要创建管道。

### P4 `npm install` 前端依赖失败：生命周期脚本被拦

**现象**
```
npm error code: 'EPERM', syscall: 'spawn'
  at runScriptPkg (@npmcli/run-script)
```
后端依赖能装（65 包），前端依赖装不了。

**定位**
日志显示失败在 `runScriptPkg` —— 是**依赖的 postinstall 脚本**在 spawn。前端依赖链里的 `esbuild` 带 postinstall。

**解决**
```bash
npm --prefix web install --ignore-scripts
```
然后验证 esbuild 的平台二进制确实在：`node_modules/@esbuild/win32-x64/esbuild.exe` 存在 → 不需要 postinstall 也能工作（二进制由可选平台包直接提供，postinstall 只是校验/兜底下载）。

**收获**
`--ignore-scripts` 不是"关掉安全检查"，而是跳过安装期脚本。执行后必须**显式验证脚本本该产生的东西是否存在**，不能装上就算完。

### P5 Vite 构建失败：esbuild 子进程

**现象**
```
Error: spawn EPERM
  at ensureServiceIsRunning (node_modules/esbuild/lib/main.js:1978)
```

**定位**
`esbuild` 以**常驻服务进程 + 管道通信**的方式工作（性能设计），这是构建链的强依赖，无法绕过或改写。

**解决**
这是硬边界，只能一次性放宽该条命令的执行权限（不改代码）。放宽后构建成功：63 模块，JS 311 KB / gzip 98.8 KB，CSS 17 KB。

**收获**
判断"能不能绕过"的标准是：失败点是否在**自己可控的代码**里。`--ignore-scripts` 能绕过安装期脚本，但改不了 esbuild 的运行时架构——这类只能调整执行环境，不要在代码里硬凑。

### P6 无头浏览器截图失败：进程间通信被拒绝

**现象**
```
FATAL:mojo\public\cpp\platform\platform_channel.cc:112] Check failed: 拒绝访问 (0x5)
crash server failed to launch, self-terminating
```

**定位**
Chrome 的多进程架构（browser / renderer / GPU）依赖 Mojo IPC，底层同样是命名管道。与 P3/P5 是**同一个根因的不同表现**。

**解决**
同样一次性放宽执行权限后截图成功，四张页面截图成为 UI 验收证据。

**收获**
当几个不相关的程序都以"拒绝访问/spawn 失败"报错时，应优先怀疑**共同的执行环境约束**，而不是挨个查程序 bug。归因线索是错误码集中（都是 5 / EPERM / EACCES）。

## 第 2 组 · 业务与实现

### P7 跨天活动显示"持续 1 天"

**现象**
活动 11-15 09:00 → 11-16 18:00（33 小时，跨两个自然日），卡片与详情页显示 **"持续 1 天"**；但同一活动在时间轴上标注 **"2 天"**。

**定位**
两处各算一套：

```js
// time.js（卡片/详情）
const diffDay = Math.round(diffMin / 1440);   // round(1.375) = 1  ← 错
// timeline.js（时间轴）
const durationDays = Math.ceil((e - s) / DAY_MS); // ceil(1.375) = 2
```

四舍五入把 1.375 天压成 1 天，而"跨了两个自然日"这件事被丢掉了。

**解决**
统一为向上取整：

```js
const diffDay = Math.ceil(diffMin / 1440);
```

**验证**（6 组边界实跑）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 33 小时（跨 2 日） | 1 天 | **2 天** ✅ |
| 同日 2 小时 | 2 小时 | 2 小时 ✅ |
| 跨月 31 天 | 31 天 | **32 天** ✅（与时间轴一致） |
| 跨月 6.3 天 | 6 天 | **7 天** ✅ |
| 近 30 天 | 30 天 | 30 天 ✅ |
| 跨年 3.2 天 | 3 天 | **4 天** ✅ |

**收获**
同一业务量（持续天数）在项目里**只能有一个算法口径**。一旦在两处各写一遍，就一定会漂移。修复时优先"统一口径"，而不是把两处都调成看起来对的值。

### P8 时间轴窄色条里的标题被裁成碎片

**现象**
时间轴上 2 天以内的活动，色条里显示的是"第七届""月""校园"这种残缺文字。

**定位**
标题被放进色条内部，用 `overflow: hidden` 裁剪。月视图下一个 2 天活动只占约 6.7% 宽度（约 60px），装不下 9 个汉字。

**解决**
按宽度分两路渲染：

- 宽度 ≥ 18%：标题放在色条**内部**（居中、白字）
- 宽度 < 18%：标题画在色条**外侧**（右侧，若右侧空间不足则换左侧）

之所以敢放外侧：**每行只有一个活动**，不会互相遮挡。

**收获**
数据可视化里，"标签放不下"不应该靠缩小字号解决，而应该按**可用空间动态选择布局策略**。这里的可用空间是行内的，不是全局的。

### P9 外侧标题仍被遮住首字

**现象**
修完 P8 后，`Linux 运维入门实操` 显示成 `inux 运维入门实操`，`AI 辅助编程边界讨论会` 显示成 `辅助编程边界讨论会`——首字被色条压住。

**定位**
极短活动的 `widthPct ≈ 0`，但 CSS 有 `min-width: 6px` 兜底保证可见性。于是**实际渲染宽度 6px，而定位用的仍是百分比理论位置**，两个坐标系不一致，标题起点落在色块内部。

**解决**
偏移量 8px → 16px（覆盖 6px 色块 + 10px 间隙），并给标题加半透明白底圆角，使其压在网格线上也可读。

**收获**
当元素同时有"百分比定位"和"像素级最小尺寸"时，两者会打架。要么统一到像素坐标系计算，要么给最小尺寸留出足够的偏移余量。这里选了后者（成本更低）。

### P10 「今天」标签压住时间刻度

**现象**
时间轴顶部的红色"今天"标签与刻度文字（11/9）重叠。

**定位**
`.tl-axis-track` 高 22px，标签用 `top: -20px` 绝对定位，结果跑到轴的上方而不是轴内。

**解决**
轴高 22px → 30px，标签改为 `top: 15px`，与刻度（`top: 0`，约 15px 高）上下分层。

**收获**
绝对定位的负偏移很容易在不同字号/行高下失控。更稳的做法是**给容器留够高度，用正向偏移分层**，而不是靠越界摆放。

### P11 状态筛选与分页的冲突

**现象（设计阶段预判）**
如果先查出全部活动、再在 JS 里过滤 `status`，那 `total` 与分页就全错了——第 2 页可能是空的，或同一活动跨页重复。

**解决**
把"状态"翻译成 SQL 条件，在数据库层过滤，让 `COUNT` 与 `LIMIT/OFFSET` 走同一套 `WHERE`：

| 状态 | SQL 条件 |
|---|---|
| `ended` | `end_at < now` |
| `ongoing` | `start_at <= now AND end_at >= now` |
| `signup_closed` | `start_at > now AND signup_deadline <= now` |
| `signup_open` | `start_at > now AND signup_deadline > now` |

因为时间统一存 UTC ISO 字符串（定长），字典序 == 时间序，可以直接用字符串比较。

**收获**
"派生字段能不能过滤"是常见陷阱。派生的**展示值**可以在 JS 算，但只要它参与**筛选或排序**，就必须下推到数据库，否则分页必然出错。

### P12 搜索框输入 `%` 会返回全部

**现象（预判 + 测试固化）**
`q=%` 若直接拼进 `LIKE '%...%'`，`%` 变成通配符，等于无条件匹配。

**解决**
转义 `\ % _` 三个字符，并给 `LIKE` 加 `ESCAPE '\'`：

```js
const like = `%${q.replace(/[\\%_]/g, (m) => `\\${m}`)}%`;
// SQL: title LIKE ? ESCAPE '\'
```

同时排序字段用**白名单枚举**映射，绝不把用户输入拼进 `ORDER BY`。

**收获**
参数化只解决"值"的注入，**不解决** `LIKE` 通配符语义和 `ORDER BY` 标识符注入。这两处必须单独处理。

### P13 `import { ErrorRequestHandler } from 'express'` 导致服务起不来

**现象**
代码审查阶段发现 `middleware/errors.js` 有一行从 `express` 导入 `ErrorRequestHandler`（那是 TypeScript 的类型导出），本项目是纯 JS。

**原因**
ESM 对**具名导入**是静态校验的：导入一个不存在的具名导出会在**模块加载时**抛 `SyntaxError`，整个服务直接起不来。这和 CommonJS 的 `undefined` 行为完全不同。

**解决**
删除该行（错误中间件靠"4 个参数"被 Express 识别，不需要类型）。

**收获**
纯 JS + ESM 项目里不要照搬 TypeScript 的类型导入。另外这类错误不会被单元测试发现——如果测试 import 的是同一模块，会是同样的加载失败，表现为"所有测试一起挂"，需要看第一条堆栈。

### P17 CI 一跑就红：`node --test test/` 在 Node 24 下根本无效

**现象**
本地 `npm run verify` 全绿（164 项），推到 GitHub 后 CI 在「后端测试」这步直接失败。日志是 403（无管理员权限下载），只能回本地复现。

**定位**
执行 CI 里那条命令：

```bash
npm --prefix server test
```

```
> sangzi-server@1.0.0 test
> node --test test/

Error: Cannot find module 'D:\作品\工作台\桑梓项目\server\test'
code: 'MODULE_NOT_FOUND'
✖ test (75.1ms)
ℹ tests 1  ℹ pass 0  ℹ fail 1
```

**原因**：Node 24 里 `node --test <路径>` 会把该路径当作**待执行的入口模块**，而 `test/` 是目录、不是模块 → 直接 `MODULE_NOT_FOUND`。目录遍历只发生在**不传任何参数**的自动发现模式。

**为什么一直没发现**
`scripts/verify.mjs` 为了绕开沙箱「禁止管道式 spawn」的限制（见 P3），早已改成**逐文件运行** `node <file>`。

```
npm test          → node --test test/        ← 坏的，CI 走这条
npm run verify    → node test/x.test.js ...  ← 好的，我本地一直走这条
```

**两条路径执行的代码不同**，所以脚本自身的 bug 被完全掩盖了。前端脚本此前已改成 `node --test`（无目录参数），因此只有后端中招。

**解决**

```json
"test": "node --test"
```

依靠自动发现：递归匹配 `**/*.test.js`，自动跳过 `node_modules`。

修复后本地复现三条 CI 命令，全部通过：

| 步骤 | 结果 |
|---|---|
| `npm --prefix server test` | ✅ 101 项通过 |
| `npm --prefix web test` | ✅ 63 项通过 |
| `npm --prefix web run build` | ✅ 构建成功 |

**收获**

1. **「本地全绿」不等于「CI 会绿」**。只要两条路径不完全一致，就有可能在 CI 才暴露。
2. **为适配受限环境引入的替代执行方式，会降低对真实入口的覆盖**。替代方案必须标注「这条路径与正式路径不同」，否则它会变成一层虚假的安全感——本项目正是如此：`verify` 越绿，越没有人去跑 `npm test`。
3. **CI 的独特价值**：它是唯一不经过我们任何"便利绕行"的路径。这件事本身就是把 CI 补上的最好理由。

## 第 3 组 · 无障碍与移动端（优化阶段）

### P15 375px 下整页横向溢出

**现象**
在 375px 视口截图，页面右侧被裁：首页说明文字「点开卡片可以查看报名方式与学长学姐的经验」被切掉半句，导航「我的发布」只显示到「我的」。

**定位**
两处独立原因：

1. **导航太宽**：品牌文字「桑梓活动聚合」+ 4 个导航项，在 375px 下总宽约 431px，直接撑破
2. **flex 子项按 max-content 计算**：`.page-head` 是 `display:flex`，子项默认 `flex-basis: auto` 且 `min-width: auto`，长段落会按内容宽度撑开而**不换行**，把容器顶宽

**解决**

| 层 | 改动 |
|---|---|
| 导航 | `≤480px` 隐藏品牌文字（只留图标）、缩小链接内边距与字号 |
| 页面标题区 | `.page-head > div { min-width: 0; flex: 1 1 260px }`，让文本正常换行 |
| 主内容 | `.main { min-width: 0 }` |
| 兜底 | `.shell { overflow-x: clip }` |

> 兜底为什么用 `clip` 而不是 `hidden`：`hidden` 会创建滚动容器，干扰时间轴内部自己的横向滚动；`clip` 只裁剪、不创建滚动容器。

**收获**
**`min-width: auto` 是 flex 子项在移动端横向溢出的头号原因。** 另外 `overflow-x: hidden` 能让页面"看起来好了"，但那是掩盖——内容仍被裁掉、仍不可用。必须先修根因，再考虑兜底。

### P16 无头浏览器 `--window-size=375` 不生效，导致误判"CSS 没改对"

**现象**
改完移动端样式后重新构建、重新截图，导航里的品牌文字**仍然显示**，一度判断 CSS 规则没生效。

**定位**
对比截图里生效的样式：导航字号 13px（720 断点）、筛选器两列（720 断点）——说明**真实视口在 481–720 之间，不是 375**。Windows 对 Chrome 窗口有最小宽度限制，`--window-size=375,900` 只决定了截图尺寸，没有决定布局视口。

**验证方式**
把页面放进一个 `width: 375px` 的 `<iframe>` 再截图：子文档视口就是 375，媒体查询按 375 求值。结果 480 断点立即生效（品牌文字隐藏、四个导航项放得下），**确认 CSS 本来就是对的，是测量工具骗了我**。

**收获**
**验证工具本身也会说谎。** 当"改了没反应"时，先确认工具是否真的在测你想测的条件（这里是视口宽度），再怀疑代码。判别方法很实用：挑一个只在该断点生效的样式，看它有没有应用——没应用说明断点根本没命中，而不是规则写错。

## 第 4 组 · 容器化环境（未走通，如实记录）

### P14 无法启用「虚拟机平台」→ Docker Desktop 装不上

> 这一条没有修复，最终**放弃容器化**。记录它是为了说明"临时环境限制"与"项目缺陷"的区别，以及什么时候该停止投入。

**现象**

依次踩到四个错误，全部围绕同一件事——在 Windows 上跑 WSL2：

| # | 操作 | 结果 |
|---|---|---|
| 1 | `wsl --install` | 下载 WSL 包超时 |
| 2 | 微软商店搜索 WSL | 区域不提供该软件 |
| 3 | 装完 WSL MSI 后 `DISM /Enable-Feature:VirtualMachinePlatform` | **错误 14098：组件存储已损坏** |
| 4 | `DISM /Cleanup-Image /RestoreHealth` | **错误 0x800f0915：在任何位置都找不到修复内容** |

Docker Desktop 安装器的报错是同一根因的下游表现：
> Installation failed. One prerequisite is not fulfilled. Docker Desktop requires the "Virtual Machine Platform" Windows feature, which is not enabled.

**逐层定位**

1. **网络层**：GitHub 直连 TCP 443 超时（6s），但微软 / Docker 域名均可达。因此 `wsl --install` 超时是**下载通道**问题，不是断网。
   - 绕过方式：通过本机代理读取 GitHub release 页面（**不是 API**）。
   - 中途踩坑：`api.github.com` 返回 403，一度以为被封。读响应头后确认是 **`x-ratelimit-remaining: 0`，匿名配额被代理出口 IP 上其他人用光**。而 `github.com` 网页返回 200 —— 说明只要绕开 API 就能拿到文件。
   - 拿到真实资产名 `wsl.3.0.5.0.x64.msi`（注意不是猜测的 `Microsoft.WSL.3.0.5.0.x64.msi`），下载 350.75 MB，**大小与 content-length 一致、MSI 魔数正确、Authenticode 签名 Valid（Microsoft Corporation）**，安装成功。

2. **系统功能层**：WSL 运行时装好了（`WslService` RUNNING），但 `vmcompute` 与 `LxssManager` 服务**不存在** → 「虚拟机平台」与「Linux 子系统」两个可选功能未启用。

3. **组件库层**：启用功能时 CBS 在 finalize 阶段返回 `0x80073712`（`ERROR_SXS_COMPONENT_STORE_CORRUPT`）。

4. **修复层**：
   - `ScanHealth` 耗时约 45 分钟，结论"可以修复组件存储"——**但这只表示理论上可修，不代表本地有源**。
   - `RestoreHealth` 跑到 84.9% 后报 `0x800f0915`：Windows Update 未为当前 build（26200.9711）提供匹配修复包，本机也无备用源。
   - 唯一确定解法是提供同版本 ISO 作 `/Source`，代价约 5.9 GB 下载 + 不确定的成功率。

**决策：停止投入**

判定依据不是"还能不能再试"，而是三个事实：

- 项目主体已 100% 完成并验证（164 项测试、生产模式接口探测、四页截图核对）；
- Docker 属**选做加分项**，不影响基础要求；
- 继续需要 3–4 小时且结果不确定，投入产出不成立。

最终处理：容器化材料（`deploy/Dockerfile`、`docker-compose.yml`）**保留在仓库并逐行审查**，但 README 与 `docs/04` 中明确标注 **❌ 未能验证**，绝不含糊成"已支持 Docker"。

**后续修正（2026-11-11）：真实原因不是组件库损坏，容器化已跑通**

上一轮的结论有误，实测推翻：

| 时间 | 事实 | 证据 |
|---|---|---|
| 11-10 18:44 | `C:\Windows\WinSxS\pending.xml` 存在（183 KB），`CBS RebootPending=True` —— **WSL 的 MSI 装好后从未重启**，遗留 CBS 挂起事务（`Microsoft-Windows-Lxss-merged-Deployment` + `dual_wvms` 驱动） | `pending.xml`、`CBS.log` |
| 11-10 18:07 | 报 `0x80073712` 的真触发点是 `vmwp.exe.mui`（Hyper-V VMWP 的 zh-CN 资源）压缩态异常：磁盘 88,576 B 未压缩，组件清单却要求 LZMS 压缩 | `CBS.log`：`Unexpected compression state ... LZMS: 3` |
| 11-11 12:44 | **重启后**挂起事务正常收尾（`Lxss-merged-Package → Installed`） | `CBS.log`：`completed startup processing` |
| 11-11 12:51 | 提权重跑 `Enable-Feature`，**两个功能均返回 `0x0 (S_OK)`**，`0x80073712` 未再出现 | `DISM`：`overall result:0x0 (S_OK)` |
| 11-11 15:0x | 重启后 `vmcompute` 服务出现，`hello-world` 可运行 | `Get-Service vmcompute` |

**结论**：根因是「装完 WSL MSI 后未重启」导致 CBS 事务无法合并；那个单个损坏的 `vmwp.exe.mui` 被更新的组件（10.0.26100.9711）取代而自然绕过。**没有下载任何 ISO，节省 5.9 GB。**

**修正后的最终处理**：Docker Desktop 4.99.0 已装通并迁移到 E 盘，项目容器化方案**已完成全量验证**（构建 30s、`healthy`、`/api/health` `db=ok`、`restart` 后数据持久化），README / docs/04 / docs/05 中的「未验证」表述已同步改为「已验证」。

**这条最值得记住的教训**

原来的判断是「错误码 = 组件库损坏 = 需要 ISO 重装」。**错误码描述的是症状，不是原因。** 如果当时先查 `pending.xml` / `RebootPending`，就能在 5 分钟内定位到「缺一次重启」，而不是花 2 小时、还差点下载 5.9 GB 镜像。**在 Windows 上遇到 CBS/DISM 类错误，第一步永远是确认有没有挂起的事务和未完成的重启。**

**收获**

1. **"可修复"不等于"有源可修"**。`ScanHealth` 与 `RestoreHealth` 回答的是不同问题，前者不保证后者能成功。
2. **403 要先看响应头和响应体，再谈"被封"**。`x-ratelimit-remaining: 0` 一读就知道是限流；换条路（网页代替 API）即可绕开。
3. **未验证就要说未验证**。把"写完但没跑通"包装成"支持 Docker"，只会在答辩被追问时翻车；如实标注的损失远小于被揭穿。
4. **设时间盒并执行它**。环境问题最容易无限吸时间，因为每一步看起来都"就差一点"。判断标准应是"这项是否影响交付"，而不是"是否还能再试一次"。
5. **但设了时间盒不等于结论就是对的**。这一条被推翻正说明：暂停投入是对的，但停在错误结论上、不再回头看，就会把错误认知带进交付文档。时间盒管的是"要不要继续投入"，不是"结论是否正确"。

## 排查方法论小结（可直接口述）

1. **先读错误码，再读文字**。`EPERM` / `5` / `EACCES` 指向权限与跨进程边界，`ENOENT` 指向路径，`SyntaxError` 指向加载期。
2. **多程序同时报同一类错 → 怀疑共同环境**，不要逐个查 bug（P3/P5/P6 同一个根因）。
3. **区分"代码错"和"环境错"**。判断标准：失败点是否在自己可控的代码里。
4. **接口全绿 ≠ 界面正确**。P7–P10 四个问题都是后端测试 100% 通过、只有浏览器渲染才能发现的，所以加了一步截图验收。
5. **同一业务口径只能有一处实现**（P7）。发现两处算法不一致时，先统一，再谈哪个更"对"。
6. **修完必须用边界数据验证**，不能只看主流程。P7 的 6 组边界、时间轴的 E1–E14 都是这个原则。
7. **环境问题要设时间盒并真的执行**（P14）。判断停不停的标准是"是否影响交付"，不是"是否还能再试一次"。
8. **未验证就不要说成已验证**。宁可写 "❌ 未能验证 + 原因"，也不要含糊成"已支持"。
