# 12 · 容量基线与压测

> 运维方向的核心材料之一：**没有数字的"性能还行"没有意义。**
> 本文记录 2026-11-23 在本机实测的容量基线，以及从数据里看到的瓶颈。

---

## 1. 测试方法

**工具**：`scripts/loadtest.mjs`（自写，零依赖，约 90 行）

```bash
node scripts/loadtest.mjs <url> --duration=8 --concurrency=10 --label=xxx [--method=POST --bodyFile=x.json]
```

- 固定并发数持续发请求，记录**每个请求的真实延迟**（不是平均值）
- 输出 RPS、P50 / P95 / P99、状态码分布、错误数
- 用 Node 内置 `fetch`，必须 `await res.arrayBuffer()` 读完 body —— 否则连接不释放，测出来的是连接数而不是吞吐

**为什么不引 k6 / autocannon**：需求只是"同机对比 + 找瓶颈"，自写脚本够用，且不增加依赖。

---

## 2. 实测结果

测试机：Windows 11 / Node 24.15 / 单进程 Express + SQLite（WAL）
场景：`GET /api/activities?pageSize=20`（14 条活动，含评论计数子查询）

### 2.1 应用直连（绕过反代，测应用本身）

| 场景 | 并发 | RPS | P50 | P95 | P99 | 请求数 | 错误 |
|---|---|---|---|---|---|---|---|
| 读列表 | 10 | **5,124.7** | 1.7 ms | 2.5 ms | 8.7 ms | 41,008 | 0 |
| 读列表 | 50 | **1,944.4** | 24.7 ms | 33.0 ms | 38.0 ms | 11,711 | 0 |
| 写入（POST） | 5 | **325.9** | 14.7 ms | 19.9 ms | 27.5 ms | 2,611 | 0 |

### 2.2 经 Nginx 反代（端到端）

| 场景 | 并发 | RPS | P50 | P95 | P99 | 请求数 | 错误 |
|---|---|---|---|---|---|---|---|
| 读首页 `/` | 10 | **2,902.5** | 3.2 ms | 4.5 ms | 8.7 ms | 23,226 | 0 |

反代引入的额外延迟：P50 从 **1.7 ms → 3.2 ms**（约 +1.5 ms），属于典型的一次代理转发开销。

### 2.3 限流验证

连发 80 个并发请求到 `/api/health`（限流阈值 20 r/s、burst 40）：

| 状态码 | 数量 | 说明 |
|---|---|---|
| 200 | 42 | 在允许的突发额度内 |
| **429** | **38** | 被 `limit_req` 拒绝 |

限流按设计生效，且 **429 在 nginx 层就返回，没有打到应用**（应用日志中无对应 reqId）。

---

## 3. 从数据里读出的三个结论

### 3.1 瓶颈是「写」，不是「读」

```
读: 5,124 req/s  ┃  写: 326 req/s     → 相差约 16 倍
```

原因很明确：SQLite 是**单写者模型**，写操作串行，每次还要等 WAL 落盘。
而读可以并发（WAL 允许读写并行）。

**这个数字直接决定了架构边界**：如果校园里真的出现高频写入（比如几百人同时报名），必须换 PostgreSQL 并把写入拆到独立实例。当前设计适合"发布少、浏览多"的真实场景。

### 3.2 并发不是越高越好：50 并发比 10 并发**更慢**

| 并发 | RPS | P50 |
|---|---|---|
| 10 | 5,124 | 1.7 ms |
| 50 | 1,944 | 24.7 ms |

**吞吐下降 62%，延迟上升 14 倍。** 这是单进程 Node 的典型饱和曲线：

- 事件循环只有一个线程，50 个并发请求排队争抢
- 排队 → 上下文切换与 GC 压力上升 → 单请求耗时变长 → 吞吐反而降低

**运维含义**：超出饱和点继续加压只会让所有用户更慢，正确做法是**限流 + 多实例 + 负载均衡**，而不是继续加并发。

> 这也是为什么 Nginx 层的 `limit_req` 不是"锦上添花"而是必需品：它把超额流量挡在应用之外，保护已经在饱和边缘的单进程。

### 3.3 反代代价可接受

+1.5 ms 的 P50 开销换来 TLS 终止、gzip、限流、安全头、统一入口 —— **非常划算**。这也反过来说明：反代不该被当成"多一跳的负担"。

## 4. 这些数字的边界（必须说清）

| 限制 | 说明 |
|---|---|
| **压测程序与服务同机** | 生成压力和被压对象抢同一份 CPU 与内存，**绝对数值会偏低**，只能用于同机相对比较 |
| 单机单实例 | 没有多核集群、没有负载均衡后的横向扩展 |
| 数据量小 | 14 条活动；真实数据量下查询与索引表现需重测 |
| 未覆盖长连接与慢客户端 | 没有模拟慢网络、大文件下载、WebSocket |
| 容器内未单独测 | 应用直连数据来自宿主进程；容器内会有约 5–10% 的网络栈开销 |

**结论**：这些数字的正确用法是「**证明瓶颈在哪里**」和「**证明优化有没有效果**」，而不是承诺"系统能扛 5000 QPS"。

---

## 5. 如果要继续提升，优先级是

| 优先级 | 措施 | 预期效果 | 成本 |
|---|---|---|---|
| 1 | Nginx 层限流（已做） | 保护应用不被突发打穿 | 已完成 |
| 2 | 多进程（`node --cluster` 或 PM2 cluster） | 吃满多核，吞吐线性提升 | 中（需处理 SQLite 多进程写入） |
| 3 | 读缓存（列表结果缓存 5–10 秒） | 读场景再提升数倍 | 低 |
| 4 | 迁移 PostgreSQL | 解决写入瓶颈，支持多实例 | 高 |
| 5 | 静态资源交给 Nginx 直出 | 减少 Node 处理静态请求 | 中 |

**注意第 2 项的真实约束**：SQLite 多进程写入会加重锁竞争，所以"多进程"通常要配合"写操作集中到单进程"或直接上 PG。这也是为什么第 4 项排在第 2 项之后 —— 不是不能做，而是顺序错了会白做。

## 6. 复现方式

```bash
# 1) 起宿主服务（用独立库，不污染正式数据）
cd server
NODE_ENV=production DB_PATH=./data/loadtest.db PORT=3101 node src/index.js

# 2) 灌种子数据
node src/seed.js

# 3) 依次压测
node scripts/loadtest.mjs 'http://127.0.0.1:3101/api/activities?pageSize=20' --duration=8 --concurrency=10 --label=read-c10
node scripts/loadtest.mjs 'http://127.0.0.1:3101/api/activities?pageSize=20' --duration=6 --concurrency=50 --label=read-c50
node scripts/loadtest.mjs 'http://127.0.0.1:3101/api/activities' --duration=8 --concurrency=5 --method=POST --bodyFile=body.json --label=write-c5

# 4) 端到端（经 nginx）
node scripts/loadtest.mjs 'http://127.0.0.1:8080/' --duration=8 --concurrency=10 --label=via-nginx
```
